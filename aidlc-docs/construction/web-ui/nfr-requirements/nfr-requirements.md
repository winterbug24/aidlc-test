# NFR 요구사항 - web-ui

요구사항 문서(`aidlc-docs/inception/requirements/web-ui-requirements.md`) 4장의 NFR을 측정 가능한 수준으로 구체화한다.
1차 워크플로의 NFR 요구사항(`aidlc-docs/construction/todo-api/nfr-requirements/nfr-requirements.md`)은 그대로 유효하며, 이 문서는 추가되거나 달라지는 것만 다룬다.
근거 표기: WNFR-Q는 이 단계의 질문 번호를 가리킨다.

## 1. 전제와 가정

| 항목 | 내용 |
|---|---|
| 실행 환경 | 서버는 WSL Ubuntu, 화면은 Windows의 Edge 또는 Chrome 최신 버전 |
| 사용 규모 | 사용자 1명, 브라우저 탭 한두 개, 활성 항목 수천 건 이하 (1차와 같음) |
| 화면 구성 | 화면 문서 1개, 스타일 1개, 스크립트 1개. 빌드 단계 없음 |
| 통신 | 루프백 HTTP. 화면과 API는 같은 출처 |

## 2. 보안

### 2.1 응답 헤더 (SECURITY-04)

아래 헤더를 **모든 응답**(화면 파일과 기존 API의 JSON 응답 모두)에 붙인다. 화면 응답에만 붙이는 것보다 빠뜨릴 위험이 없다. 기존 API 응답에 헤더가 더해지지만 본문과 상태 코드는 바뀌지 않는다.

| ID | 헤더 | 값 |
|---|---|---|
| WSEC-01 | `Content-Security-Policy` | `default-src 'none'; script-src 'self'; style-src 'self'; connect-src 'self'; img-src 'self' data:; base-uri 'none'; form-action 'none'; frame-ancestors 'none'` |
| WSEC-02 | `Strict-Transport-Security` | `max-age=31536000; includeSubDomains` |
| WSEC-03 | `X-Content-Type-Options` | `nosniff` (기존 유지) |
| WSEC-04 | `X-Frame-Options` | `DENY` |
| WSEC-05 | `Referrer-Policy` | `strict-origin-when-cross-origin` |
| WSEC-06 | `Cache-Control` | `no-store` (기존 유지. 화면 파일에도 적용) |

콘텐츠 보안 정책의 의미:
- 기본은 모두 차단한다. 같은 출처의 스크립트 파일, 스타일 파일, API 호출만 허용한다
- 인라인 스크립트, 인라인 스타일, `eval`은 허용하지 않는다 (`unsafe-inline`, `unsafe-eval` 없음)
- 외부 출처의 어떤 자원도 불러올 수 없다
- 다른 페이지가 이 화면을 프레임에 넣을 수 없다
- `img-src`의 `data:`는 브라우저가 아이콘 파일을 따로 요청하지 않게 하는 빈 아이콘 선언에만 쓴다. 스크립트 실행과는 무관하다

`Strict-Transport-Security`는 HTTP 루프백에서 브라우저가 무시한다. 규칙 요건을 충족하려고 보내며 실제 효과는 없다 (요구사항 단계에서 승인됨).

## 8. 설정 항목

새 환경 변수는 추가하지 않는다. 화면 주소 경로(`/api_test`), 후보 포트 범위(8000~8009), 제한 시간 값은 코드의 상수로 둔다.

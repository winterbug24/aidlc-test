# NFR 설계 패턴 - web-ui

NFR 요구사항(`../nfr-requirements/nfr-requirements.md`)의 각 항목을 어떤 패턴으로 충족하는지 정의한다.
1차의 패턴(`aidlc-docs/construction/todo-api/nfr-design/nfr-design-patterns.md`의 SP, RP, OP, PP, TP)은 그대로 유지되며, 여기서는 추가되거나 바뀌는 것만 다룬다.

## 1. 보안 패턴

### WSP-01 전 응답 보안 헤더
- 응답 헤더를 붙이는 일을 전용 컴포넌트 하나에 모은다. 지금까지 로깅 컴포넌트의 요청 훅에 있던 `nosniff`, `no-store` 설정도 이 컴포넌트로 옮긴다.
- 앱 수준의 응답 후처리 훅으로 등록해 화면 파일, API 응답, 오류 응답(401, 404, 429, 500 포함) 모두에 같은 헤더가 붙게 한다.
- 헤더 값은 상수로 한 곳에 둔다. 콘텐츠 보안 정책은 지시문 목록에서 조립해 오타와 누락을 테스트로 잡는다.
- 충족: WSEC-01~06 / SECURITY-04

### WSP-02 고정 목록 기반 화면 파일 제공
- 화면용 라우트 묶음은 "요청 이름 → (패키지 안의 고정 파일, 콘텐츠 유형)" 대응표를 가진다. 대응표에 없는 이름은 404다.
- 요청 경로의 문자열을 파일 시스템 경로로 쓰지 않는다. 경로 탈출(`..`, 인코딩된 구분자, 절대 경로)은 대응표 조회에서 걸러진다.
- 화면 문서는 고정된 파일을 그대로 보낸다. 서버가 값을 끼워 넣지 않는다(템플릿 미사용).
- 화면 문서 안의 스타일과 스크립트 주소는 `/api_test/`로 시작하는 절대 경로로 적는다. `/api_test`와 `/api_test/` 어느 쪽으로 열어도 같은 파일을 가리킨다.
- 충족: WSEC-10, 11 / SECURITY-05, 09

### WSP-03 공개 묶음의 분리와 명시
- 화면용 라우트 묶음은 `/todos` 묶음과 별개다. 인증 훅을 걸지 않으며, 묶음 정의에 "의도적 공개: 데이터와 키를 포함하지 않는 화면 파일만 제공"이라고 적는다.
- `/todos` 묶음의 기본 거부 인증(1차 SP-01)은 건드리지 않는다. 화면이 추가돼도 보호 범위가 줄지 않음을 테스트로 고정한다.
- 충족: WSEC-12 / SECURITY-08

### WSP-04 텍스트 전용 화면 갱신
- 스크립트는 화면 요소를 만들 때 요소 생성과 텍스트 대입만 쓴다. 문자열을 마크업으로 해석하는 대입 방식은 코드 전체에서 쓰지 않는다.
- 화면 문서의 구조(영역, 버튼, 확인 창)는 HTML 파일에 미리 두고, 스크립트는 보이기/숨기기와 목록 항목 생성만 한다. 목록 항목은 HTML의 견본 요소를 복제해 만든다.
- 콘텐츠 보안 정책(WSP-01)이 인라인 스크립트를 막으므로, 이 규칙이 깨져도 주입된 스크립트는 실행되지 않는다 (이중 방어).
- 충족: WSEC-21 / SECURITY-05, 11

### WSP-05 키의 단일 경로
- 키는 KeyStore(저장), ApiClient(헤더로 전송) 두 곳만 지난다. 다른 코드는 키 값을 받지 않고 "키가 있는지"만 묻는다.
- 키를 주소, 화면의 글자, 콘솔, 오류 문구에 넣는 코드를 두지 않는다. 브라우저 테스트가 주소와 콘솔 출력에 키가 없는지 확인한다.
- 충족: WSEC-20, 22 / SECURITY-03

### WSP-06 실행 파일의 비밀 취급
- 키 생성은 표준 라이브러리의 암호학적 난수 기능을 쓴다. 키 파일은 처음부터 소유자 전용 권한으로 만든다.
- 서버 프로세스에는 키를 환경 변수로 넘긴다. 클립보드 프로그램에는 표준 입력으로 넘긴다. 어떤 프로세스의 명령줄 인자에도 키가 없다.
- 실행 파일의 모든 출력 문구는 키 값을 포함하지 않는다. 테스트가 출력에 키가 없는지 확인한다.
- 충족: WSEC-30~32 / SECURITY-12

### WSP-07 WSL 안에서만 하는 서버 식별
- "이 포트의 서버가 우리 서버인가"는 WSL 안에서 그 포트의 `/todos`를 키로 호출해 판정한다. 대상은 `127.0.0.1`의 후보 포트뿐이다.
- 이 서버는 항상 WSL에서 실행되므로 Windows 쪽으로는 키가 든 요청을 보내지 않는다. Windows 프로그램은 키를 받지 않는다.
- 충족: WSEC-33. 기능 설계의 수용 위험 범위를 줄인다

## 2. 복원력 패턴

### WRP-01 제한 시간이 있는 단일 호출 경로
- 화면의 모든 API 호출은 ApiClient의 한 함수를 지난다. 이 함수가 제한 시간(15초)과 중단을 적용하고, 결과를 세 가지로만 돌려준다: 성공(데이터), 서버 거부(상태 코드, 서버 문구, 재시도 대기 시간), 연결 실패.
- 호출한 쪽은 세 가지만 처리하면 되므로 예외가 새어 화면이 멈추는 경로가 없다.
- 응답 본문이 JSON이 아니어도 실패로 정리해 돌려준다.
- 충족: WREL-01, 02 / RESILIENCY-10

### WRP-02 실패 시 상태 보존
- 목록 요청이 실패하면 화면의 목록을 바꾸지 않는다. 완료 체크가 실패하면 체크 상태를 되돌린다. 추가가 실패하면 입력 내용을 남긴다.
- 불러오는 중 표시는 요청이 어떻게 끝나든 반드시 내린다.
- 충족: WR-25, 26, 35, 41 / RESILIENCY-10

### WRP-03 최신 요청만 반영
- 목록 요청마다 일련번호를 매기고, 응답이 왔을 때 가장 최근 번호가 아니면 버린다.
- 충족: WR-27

### WRP-04 한 번에 읽는 포트 상태 판정
- 판정을 세 가지 확인으로 나눈다.
  - 우리 서버인지: WSL 안에서 키로 `/todos` 호출 (WSP-07)
  - WSL 쪽 사용 여부: WSL 안에서 그 포트에 연결을 시도
  - Windows 쪽 사용 여부: Windows의 수신 포트 목록을 한 번 읽어 후보 포트가 들어 있는지 확인
- Windows에서 닫힌 포트에 연결을 시도하면 실패 판정까지 약 2초가 걸리므로, 포트마다 연결하지 않고 목록을 한 번만 읽는다.
- Windows 쪽 목록을 읽을 수 없으면(WSL에서 Windows 프로그램 호출이 꺼진 환경) 경고를 표시하고 WSL 쪽 확인만으로 진행한다.
- 판정 결과(포트별 `ours`, `busy`, `free`)를 순수 함수인 포트 선택 로직에 넘긴다.
- 충족: WREL-04, WR-83~85

### WRP-05 응답 확인 후 화면 열기와 확실한 정리
- 서버 프로세스를 시작한 뒤 `/health`가 200을 줄 때까지 0.5초 간격으로 최대 20초 확인하고, 그다음에 브라우저를 연다.
- 대기 중 서버 프로세스가 먼저 끝나면 기다리지 않고 바로 실패로 처리한다.
- 실패하면 시작한 서버 프로세스를 끝내고 로그 위치를 안내한다.
- 실행 파일은 종료 신호(Ctrl+C, 창 닫힘)를 받으면 서버 프로세스를 끝낸다. 실행 파일이 강제로 죽는 경우에도 서버가 남지 않도록, 서버 프로세스에 "부모가 끝나면 함께 끝난다"는 설정을 건다.
- 충족: WREL-03, 05, 06 / RESILIENCY-06

| WDP-05 | 표준 요소(버튼, 체크 상자, 양식, 대화 상자)를 그대로 쓰고 키보드 동작을 새로 만들지 않는다 | WUX-06 |

## 5. 테스트 용이성 패턴

| ID | 패턴 | 충족 |
|---|---|---|
| WTP-01 | 브라우저 테스트는 테스트 안에서 실제 앱을 임의의 빈 포트에 띄우고 임시 DB를 쓴다. 테스트마다 새 앱과 새 브라우저 컨텍스트를 써서 저장된 키와 데이터가 섞이지 않게 한다 | WTST-03, 11 |
| WTST-07 구현 | 모든 브라우저 테스트에 공통 장치를 걸어, 콘솔 오류나 콘텐츠 보안 정책 위반이 한 번이라도 나면 그 테스트를 실패시킨다 | WTST-07 |
| WTP-02 | 준비 데이터는 화면을 거치지 않고 API나 저장소로 직접 넣는다. 테스트는 검증하려는 동작만 화면으로 수행한다 | 속도와 안정성 |
| WTP-03 | 서버 실패 상황(503, 429, 연결 끊김, 응답 지연)은 브라우저 테스트 도구의 요청 가로채기로 만든다. 실제 서버를 망가뜨리지 않는다 | US-17, US-18 |
| WTP-04 | 실행 파일의 로직을 세 층으로 나눈다: 순수 계산(포트 선택, 키 파일 형식), 환경 확인(포트 상태, 서버 응답), 부수 효과(프로세스 시작, 클립보드, 브라우저). 순수 계산은 속성 기반 테스트로, 환경 확인은 실제 소켓과 테스트용 앱으로, 부수 효과는 바꿔 끼울 수 있는 함수로 두어 가짜로 대체해 테스트한다 | WTST-09, 10 |
| WTP-05 | 요소 선택은 `data-testid`로만 한다. 문구나 모양이 바뀌어도 테스트가 깨지지 않는다 | WNFR-UX-06 |

## 6. 수동 확인이 필요한 항목

자동화할 수 없어 Build and Test 지침의 수동 확인 절차로 넘기는 항목이다.

| 항목 | 이유 |
|---|---|
| 배치 파일을 더블클릭했을 때의 동작 (서버 시작, 브라우저 열림) | Windows 탐색기와 WSL 사이의 동작 |
| 실행 창을 닫았을 때 서버가 남지 않는지 | 창 닫힘 신호의 전달 |
| 바로 가기로 실행했을 때의 동작 | Windows 셸 동작 |
| 실제 Edge와 실제 Chrome에서의 모습 비교 | 자동 테스트는 Chromium 하나만 사용 |
| Windows 화면 배율 125%, 150% | 운영체제 설정 |
| Windows의 밝게/어둡게 설정을 실제로 바꿨을 때의 전환 | 자동 테스트는 브라우저의 색 구성 흉내만 사용 |

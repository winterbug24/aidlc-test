# 업무 로직 모델 - web-ui

규칙 번호(WR-xx)는 `business-rules.md`, 상태 이름은 `domain-entities.md`를 가리킨다.

## 1. 화면의 동작별 흐름

### 1.1 화면 열기 (US-05, US-06)
```text
1. 화면 모드 = starting
2. 브라우저 저장소에서 키를 읽는다
3. 키 없음 -> 화면 모드 = key, 끝
4. 키 있음 -> 목록 조회 (필터 = all)
   - 200 -> 목록 반영, 화면 모드 = list
   - 401 -> 키와 목록 지움, 안내(WR-18), 화면 모드 = key
   - 그 밖의 실패 -> 화면 모드 = list (빈 목록), 응답 처리 규칙에 따른 안내
```
API 호출: 0회(키 없음) 또는 1회.

### 1.2 키 제출 (US-05, US-15, US-17)
```text
1. 입력값의 앞뒤 공백 제거 (WR-10)
2. 비어 있으면 안내하고 끝 (WR-11)
3. 그 키로 목록 조회 (필터 = all)
   - 200 -> 키 저장, 목록 반영, 화면 모드 = list, 입력 칸 비움
   - 401 -> "API 키가 올바르지 않습니다" (WR-13), 입력 칸 내용 선택 상태로 유지
   - 429 -> 요청 제한 안내 (WR-14)
   - 그 밖의 실패 -> 응답 처리 규칙에 따른 안내
```
API 호출: 1회. 키는 200일 때만 저장한다 (UI-INV-02).

### 1.3 키 지우기 (US-07)
```text
1. 브라우저 저장소의 키 삭제
2. 목록, 필터(all로), 안내를 초기화
3. 화면 모드 = key, 키 입력 칸에 포커스
```
API 호출: 0회.

### 1.4 목록 불러오기 (새로고침, 필터 변경) (US-12, US-13)
```text
1. 불러오는 중 = 참
2. 현재 필터로 목록 조회 (WR-21)
3. 응답이 가장 최근에 보낸 요청의 것이 아니면 버림 (WR-27)
4. 200 -> 목록 교체, 이전 안내 지움
   실패 -> 기존 목록 유지 (WR-26), 응답 처리 규칙에 따른 안내
5. 불러오는 중 = 거짓 (성공, 실패 모두)
```
필터 변경은 선택 표시를 먼저 바꾸고 위 흐름을 실행한다. API 호출: 1회.

### 1.5 할 일 추가 (US-09, US-16)
```text
1. 입력값의 앞뒤 공백 제거. 비어 있으면 안내하고 끝 (WR-31)
2. 추가 요청 진행 중이면 무시 (WR-36)
3. POST /todos {title}
   - 201 -> 필터가 all 또는 pending이면 목록 맨 위에 넣음, completed면 정보 안내 (WR-34)
            입력 칸 비우고 포커스, 이전 안내 지움
   - 실패 -> 입력 칸 유지 (WR-35), 응답 처리 규칙에 따른 안내
```
API 호출: 1회.

### 1.6 완료 체크와 해제 (US-10)
```text
1. 그 항목이 처리 중이면 무시 (WR-44)
2. 화면의 체크 상태를 즉시 바꿈, 항목을 처리 중으로 표시
3. PATCH /todos/<id> {completed}
   - 200 -> 응답 값으로 항목 갱신. 현재 필터에 해당하지 않으면 목록에서 뺌 (WR-42)
   - 404 -> "이미 삭제된 할 일입니다", 목록에서 뺌 (WR-63)
   - 그 밖의 실패 -> 체크 상태를 원래대로 (WR-41), 응답 처리 규칙에 따른 안내
4. 처리 중 표시 해제
```
API 호출: 1회.

### 1.7 삭제 (US-11)
```text
1. 삭제 버튼 -> 삭제 대기 항목 = 그 항목, 확인 창 열기, 포커스는 "취소" (WR-50, WR-51)
2. 취소(버튼, Esc, 바깥 클릭) -> 확인 창 닫기, 삭제 대기 항목 = 없음, 포커스 복귀. 끝
3. 삭제 확인 -> 확인 창 닫기, 항목을 처리 중으로 표시
4. DELETE /todos/<id>
   - 204 -> 목록에서 뺌, 이전 안내 지움
   - 404 -> "이미 삭제된 할 일입니다", 목록에서 뺌 (WR-63)
   - 그 밖의 실패 -> 항목 유지, 응답 처리 규칙에 따른 안내
5. 처리 중 표시 해제
```
API 호출: 0회(취소) 또는 1회.

### 1.8 동작별 API 호출 수 요약 (WNFR-PERF-02: 동작당 2회 이내)

| 동작 | 호출 |
|---|---|
| 화면 열기 | 0~1 |
| 키 제출 | 1 |
| 키 지우기 | 0 |
| 새로고침, 필터 변경 | 1 |
| 추가 | 1 |
| 완료 체크 | 1 |

화면은 가만히 두면 요청을 보내지 않는다 (AC-13.2).

## 2. 화면이 사용하는 API

기존 API를 그대로 쓴다. 새 엔드포인트는 화면 파일 제공뿐이다.

| 용도 | 호출 | 성공 | 화면이 처리하는 실패 |
|---|---|---|---|
| 키 검증, 목록 조회 | `GET /todos` 또는 `GET /todos?completed=true|false` | 200 | 401, 429, 5xx, 연결 실패 |
| 추가 | `POST /todos` | 201 | 400, 401, 409, 413, 429, 5xx, 연결 실패 |
| 완료 변경 | `PATCH /todos/<id>` | 200 | 400, 401, 404, 429, 5xx, 연결 실패 |
| 삭제 | `DELETE /todos/<id>` | 204 | 401, 404, 429, 5xx, 연결 실패 |

화면은 `GET /todos/<id>`(단건 조회)와 `GET /health`를 쓰지 않는다.

## 3. 실행 파일의 흐름

### 3.1 시작 파일 (US-01, US-02, US-03)
```text
1. 자기 위치에서 WSL 배포판과 프로젝트 경로를 알아냄. 실패하면 안내하고 끝 (WR-80)
2. 가상 환경 확인. 없으면 안내하고 끝 (WR-81)
3. 키 파일 확인
   - 없음 -> 키 생성, 저장, 클립보드 복사, "화면에 붙여넣으세요" 안내 (WR-82)
   - 있음 -> 읽기만 함 (WR-91)
4. 후보 포트 8000~8009의 상태를 판정 (ours / busy / free)
5. 선택
   - ours가 있음 -> reuse(가장 낮은 ours 포트): "이미 실행 중인 서버를 사용합니다" 안내,
                    브라우저 열기, 끝 (WR-83)
   - ours 없고 free가 있음 -> start(가장 낮은 free 포트) (WR-84)
   - 둘 다 없음 -> none: 안내하고 끝 (WR-85)
6. start: 그 포트로 서버 시작
7. 서버가 응답할 때까지 대기
   - 응답 -> 브라우저로 화면 주소 열기, 창에 주소와 종료 방법 표시 (WR-87)
   - 시간 초과 -> 서버 정리, 로그 위치 안내, 끝 (WR-86)
8. 창이 열려 있는 동안 서버 동작. 창 닫기 또는 Ctrl+C로 종료 (WR-88)
```

### 3.2 포트 선택 로직 (순수 함수)

입력: 후보 포트 목록(오름차순)과 포트별 상태. 출력: `reuse(포트)`, `start(포트)`, `none` 중 하나.

| 조건 | 결과 |
|---|---|
| 상태가 `ours`인 포트가 하나 이상 | `reuse(그중 가장 낮은 포트)` |
| `ours`가 없고 `free`인 포트가 하나 이상 | `start(그중 가장 낮은 포트)` |
| `ours`도 `free`도 없음 | `none` |

상태 판정(네트워크 확인)과 선택(순수 계산)을 분리해, 선택 로직을 네트워크 없이 테스트할 수 있게 한다.

### 3.3 키 복사 파일 (US-04)
```text
1. 자기 위치에서 프로젝트 경로를 알아냄 (WR-80)
2. 키 파일 확인
   - 없음 -> "시작 파일을 먼저 실행하세요" 안내, 끝
   - 있음 -> 클립보드에 복사, "복사했습니다" 안내, 끝 (WR-89)
```

### 3.4 키 파일 형식
- 한 줄: `TODO_API_KEY=<값>`
- 읽을 때는 `TODO_API_KEY=`로 시작하는 줄의 나머지를 키로 쓴다. 앞뒤 공백과 줄바꿈은 제거한다
- 쓰기와 읽기는 왕복이 성립해야 한다 (쓴 키를 읽으면 같은 값)
- 이미 있는 키 파일은 실행 파일이 고치지 않는다

## 4. 오용 시나리오 (SECURITY-11)

| ID | 시나리오 | 대응 |
|---|---|---|
| WMU-01 | 제목에 스크립트를 넣어 화면에서 실행되게 함 (저장형 XSS). 성공하면 저장된 키를 훔칠 수 있다 | 서버에서 온 문자열은 텍스트로만 넣음 (UI-INV-06), 콘텐츠 보안 정책으로 인라인 스크립트와 외부 스크립트 차단 (WNFR-SEC-01, 02) |
| WMU-02 | 서버의 오류 문구에 스크립트가 섞여 화면에서 실행되게 함 | 오류 문구도 텍스트로만 넣음 (UI-INV-06) |
| WMU-03 | 다른 웹사이트가 이 화면을 프레임 안에 넣어 클릭을 유도함 (클릭재킹) | 프레임 삽입 금지 헤더 (WNFR-SEC-01) |
| WMU-04 | 다른 웹사이트가 사용자의 브라우저로 API를 호출함 (CSRF) | 인증이 쿠키가 아니라 요청 헤더이고 CORS를 허용하지 않아, 다른 출처의 페이지는 키 헤더를 붙인 요청을 보낼 수 없다 (WNFR-SEC-07) |
| WMU-05 | 다른 웹사이트가 이 서버 주소를 자기 도메인 이름으로 가리키게 해 화면을 읽음 (DNS 리바인딩) | 화면 파일에는 데이터와 키가 없고(WR-02), 저장된 키는 주소별로 분리되어 그 사이트의 주소에서는 읽을 수 없다. 키 없이는 `/todos`가 401이다 |
| WMU-06 | 키가 주소, 브라우저 기록, 서버 로그에 남음 | 키는 요청 헤더로만 보냄 (WR-15). 서버는 키를 로그에 남기지 않음 (기존 동작) |
| WMU-07 | 화면에서 키를 무작위로 대입함 | 기존 인증 실패 한도(분당 10회)가 그대로 적용됨 |
| WMU-08 | 화면 제공 경로로 프로젝트의 다른 파일(`.env`, DB, 소스)을 읽음 (경로 탈출) | 정해 둔 화면 파일만 제공 (WR-03) |
| WMU-09 | 같은 PC의 다른 사용자나 프로그램이 프로세스 목록에서 키를 봄 | 키를 명령줄 인자로 넘기지 않음 (WR-90) |
| WMU-10 | 어깨 너머로 실행 창이나 키 입력 칸의 키를 봄 | 창에 키를 표시하지 않음 (WR-82, WR-89), 입력 칸을 가림 (WR-16) |

**수용한 위험**
- 브라우저 저장소의 키는 평문이다. 같은 Windows 계정의 프로그램이 읽을 수 있고, WMU-01이 뚫리면 탈취된다 (요구사항에서 수용).
- 클립보드에 복사한 키는 Windows 클립보드 기록이 켜져 있으면 기록에 남는다 (스토리 단계에서 수용).
- 실행 파일이 다른 포트의 프로그램에 키 헤더를 보내 볼 수 있다: 후보 포트를 쓰는 프로그램이 이 서버인지 확인하려고 키로 `/todos`를 호출하므로, 8000~8009번에서 HTTP를 받는 다른 로컬 프로그램이 있으면 그 프로그램이 키를 받게 된다. 대상이 자기 PC의 루프백 주소뿐이라 위험이 낮다고 보지만, 원하지 않으면 판정 방식을 바꿔야 한다. 검토 시 확인이 필요하다.

## 5. 테스트 가능한 속성 (PBT-01)

| ID | 대상 | 범주 | 속성 | 강제 여부 |
|---|---|---|---|---|
| WP-01 | 포트 선택 (3.2) | Invariant | `ours`가 하나라도 있으면 결과는 `reuse`이고 그 포트는 `ours` 중 가장 낮다 | 강제 (PBT-03) |
| WP-02 | 포트 선택 | Invariant | 결과가 `start(p)`면 p는 `free`이고, p보다 낮은 후보 중 `free`는 없으며, `ours`는 하나도 없다 | 강제 (PBT-03) |
| WP-03 | 포트 선택 | Invariant | 결과가 `none`인 것은 `ours`도 `free`도 없을 때뿐이다. 결과 포트는 항상 후보 목록 안에 있고 `busy`가 아니다 | 강제 (PBT-03) |
| WP-04 | 키 파일 (3.4) | Round-trip | 유효한 키를 파일 형식으로 쓴 뒤 읽으면 같은 키가 나온다 | 강제 (PBT-02) |
| WP-05 | 키 생성 | Invariant | 만든 키는 항상 32자 이상이고 서버 설정 검증을 통과한다 | 강제 (PBT-03) |

제너레이터 (PBT-07): 후보 포트별 상태 배치(세 상태의 임의 조합, 길이 0~10), 유효한 키(32자 이상, 키 생성기가 만들 수 있는 문자 집합).

**JavaScript 쪽**: 화면 코드는 상태에 따라 화면 요소를 바꾸고 API를 호출하는 코드이며, 왕복이나 문서화된 불변 조건을 가진 순수 변환 함수가 없다. PBT 프레임워크를 도입하지 않고(Node.js 없는 구성), 화면 동작은 Playwright의 예제 기반 시나리오로 검증한다. "No PBT properties identified"로 기록한다.

# 화면(E2E) 테스트 지침

웹 화면(`/api_test`)과 Windows 실행 파일을 처음부터 끝까지 확인하는 절차다.
1부는 자동화된 브라우저 테스트, 2부는 자동화할 수 없어 사람이 직접 확인해야 하는 항목이다.

## 1부. 자동화된 브라우저 테스트

### 준비
`build-instructions.md`의 "화면 테스트용 브라우저" 절을 따라 Chromium과 시스템 라이브러리를 설치한다.

### 실행
```bash
# 화면 테스트만
.venv/bin/python -m pytest -m e2e

# 파일 하나, 테스트 하나
.venv/bin/python -m pytest tests/test_ui_todos.py
.venv/bin/python -m pytest tests/test_ui_key.py -k wrong_key

# 실패 원인을 볼 자료를 남기며 실행
.venv/bin/python -m pytest -m e2e --tracing=retain-on-failure --output=test-results
.venv/bin/python -m playwright show-trace test-results/<폴더>/trace.zip
```

- **기대 결과**: `60 passed`, 약 43초
- 테스트마다 임의의 빈 포트에 실제 앱을 띄우고 임시 DB와 새 브라우저 저장소를 쓴다. 실행 중인 서버, 실제 DB, 실제 브라우저의 저장된 키에 영향이 없다
- 브라우저는 화면 없이 실행된다. 눈으로 보며 돌리려면 `--headed`를 붙인다 (WSL에서는 WSLg가 필요하다)
- 모든 테스트는 끝날 때 스크립트 오류와 콘텐츠 보안 정책 위반이 없었는지 확인한다. 하나라도 있으면 그 테스트가 실패한다

### 실패 시
1. 실패한 테스트의 출력에서 기대한 것과 실제 화면 상태(접근성 스냅샷)를 확인한다
2. 추적 자료를 남겨 다시 실행하고 `show-trace`로 단계별 화면을 본다
3. 콘솔 오류 때문에 실패했다면 메시지에 `console:` 또는 `pageerror:`로 시작하는 내용이 나온다. "Refused to ..."는 콘텐츠 보안 정책 위반이다

## 2부. 수동 확인 절차

자동 테스트가 닿지 않는 Windows 쪽 동작이다. 화면이나 실행 파일을 고친 뒤, 그리고 처음 한 번 수행한다.
시작 전에 실행 중인 서버가 없는지 확인한다 (WSL에서 `pgrep -af todo_api.server`).

### 결과 기록
위 표의 결과 칸에 표시하고, 기대와 다른 항목은 증상을 적어 둔다. 문제가 있으면 `docs/coe-template.md` 양식으로 남긴다.

### Code Generation 중 이미 확인한 것
아래는 더블클릭이 아니라 Windows 명령 해석기로 배치 파일을 실행해 확인했다. 위 A-1, A-2, A-4의 일부에 해당하지만 더블클릭과 눈으로 보는 확인은 대체하지 못한다.
- `todo-start.bat`: WSL에서 서버가 떴고 WSL과 Windows 양쪽에서 화면이 200으로 응답했다. 서버 프로세스의 명령줄에 키가 없었다
- `todo-copy-key.bat`: 한글 안내가 출력됐고 클립보드 내용이 `.env`의 키와 같았다
- 실행 로직을 강제로 죽였을 때 서버 프로세스도 함께 끝났다

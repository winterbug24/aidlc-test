# Functional Design 계획 - web-ui

## 유닛 컨텍스트
- **유닛**: `web-ui` (화면, 화면 제공 라우트, Windows 실행 파일)
- **기준 문서**: `aidlc-docs/inception/requirements/web-ui-requirements.md`, `aidlc-docs/inception/user-stories/stories.md`(US-01~US-18), `aidlc-docs/inception/reverse-engineering/api-documentation.md`
- **경계**: 기존 API의 계약과 DB는 바꾸지 않는다. 화면은 기존 API를 그대로 호출한다
- **확인한 환경**: WSL 배포판 이름 `Ubuntu`, WSL에서 Windows의 `clip.exe`(클립보드)와 `cmd.exe`를 호출할 수 있음

## 실행 단계
- [x] 1. 유닛 컨텍스트 분석 (요구사항, 스토리, 기존 API)
- [x] 2. 설계 질문 작성 (아래 질문 1~5)
- [x] 3. 사용자 답변 수집 및 모호함 분석
- [x] 4. `domain-entities.md` 작성 - 화면이 다루는 상태(화면 상태, 저장된 키, 필터, 목록, 안내 메시지)와 실행 파일이 다루는 상태(키 파일, 포트)
- [x] 5. `business-rules.md` 작성 - 화면 전환 규칙, 입력 규칙, 응답 코드별 처리 규칙, 실행 파일의 판단 규칙
- [x] 6. `business-logic-model.md` 작성 - 동작별 처리 흐름, 실행 파일 흐름, 오용 시나리오(SECURITY-11), 테스트 가능한 속성(PBT-01)
- [x] 7. `frontend-components.md` 작성 - 컴포넌트 구성, 컴포넌트별 상태와 입력, 사용자 상호작용 흐름, 입력 검증, 컴포넌트가 호출하는 API, `data-testid` 목록
- [x] 8. 스토리 대비 점검 (US-01~US-18의 수용 기준이 설계에 모두 반영되었는지)
- [x] 9. 확장 규칙 준수 점검 (Security, Resiliency, PBT 부분 적용)
- [x] 10. 완료 메시지 제시 및 승인 요청

## 질문 평가 결과

| 범주 | 판단 |
|---|---|
| 업무 로직, 도메인 모델 | 질문 없음 - 기존 API와 스토리의 수용 기준으로 확정됨 |
| 업무 규칙 | 질문 없음 - 입력 규칙은 기존 API 규칙을 따름 |
| 데이터 흐름 | 질문 없음 - 화면과 API 사이의 흐름은 기존 계약으로 정해짐 |
| 통합 지점 | 질문 3, 4, 5 - Windows와 WSL 사이의 실행 파일 동작 |
| 오류 처리 | 질문 1 - 안내를 어떤 형태로 보여 줄지 |
| 업무 시나리오 | 질문 없음 - 스토리 여정 4에서 정리됨 |
| 프런트엔드 컴포넌트 | 질문 1, 2 - 안내 표시와 삭제 확인의 형태 |

질문 없이 설계에서 정하는 항목:
- 완료 항목은 취소선과 흐린 색으로 표시하고 목록 안의 순서는 바꾸지 않는다
- 완료 체크는 누르는 즉시 화면에 반영하고 서버가 거부하면 되돌린다. 추가와 삭제는 서버 응답을 받은 뒤 반영한다
- 필터는 화면을 열 때마다 "전체"로 시작한다 (스토리 AC-12.1)
- 빈 포트 탐색 범위는 8000~8009번이다
- 실행 중인 서버가 이 To-Do 서버인지는 "키 파일의 키로 `/todos`를 호출해 200이 오는지"로 판정한다. 기존 API를 바꾸지 않고 다른 프로그램과 확실히 구분할 수 있다

C) Other (please describe after [Answer]: tag below)

[Answer]: A

## Question 2
삭제 확인은 어떤 형태로 할까요?

A) 항목 줄 안에서 확인 - 삭제 버튼을 누르면 그 줄에 "삭제할까요? 되돌릴 수 없습니다 [삭제] [취소]"가 나타남 (화면 흐름이 끊기지 않고 테마와 어울림)

B) 화면 가운데에 뜨는 확인 창(모달) - 배경을 가리고 확인/취소를 묻는 창 (눈에 잘 띔)

C) 브라우저 기본 확인 창 - 브라우저가 제공하는 표준 창 (가장 단순하지만 모양을 바꿀 수 없고 테마를 따르지 않음)

D) Other (please describe after [Answer]: tag below)

[Answer]: B

## Question 3
Windows 실행 파일은 어디에 두고 쓸 예정인가요? (실행 파일이 프로젝트 위치를 알아내는 방식이 달라집니다.)

A) 프로젝트 폴더에 두고, Windows 바탕화면이나 시작 메뉴에는 "바로 가기"를 만들어 사용 - 실행 파일이 자기 위치에서 프로젝트 경로를 알아냄. 프로젝트를 옮겨도 그대로 동작

B) 실행 파일 자체를 바탕화면 등으로 복사해 사용 - 실행 파일 안에 WSL 배포판 이름(`Ubuntu`)과 프로젝트 경로(`/home/winterbug/aidlc-test`)를 적어 둠. 프로젝트를 옮기면 파일을 고쳐야 함

C) Other (please describe after [Answer]: tag below)

[Answer]: A

## Question 4
실행 파일로 띄운 서버는 어떻게 끌까요?

A) 실행 창이 열려 있는 동안만 서버가 동작 - 창을 닫거나 창에서 Ctrl+C를 누르면 서버가 꺼짐 (켜짐/꺼짐이 눈에 보이고 단순함. 창 하나가 계속 떠 있음)

B) 서버를 창 없이 백그라운드로 띄우고, 끄는 실행 파일을 따로 제공 - 시작 파일은 화면을 연 뒤 창이 닫힘. 끄려면 종료용 파일을 실행 (창이 남지 않음. 켜 둔 것을 잊기 쉬움)

C) Other (please describe after [Answer]: tag below)

[Answer]: A

## Question 5
이미 만들어진 키를 다시 클립보드로 복사하는 방법은 어떻게 제공할까요? (다른 포트나 다른 브라우저에서 키를 다시 입력할 때 필요합니다. 처음 키를 만들 때는 자동으로 복사됩니다.)

A) 키 복사 전용 실행 파일을 따로 제공 - 더블클릭하면 키를 클립보드에 복사하고 알림 후 종료

B) 시작 실행 파일이 서버를 띄울 때마다 키를 클립보드에 복사 - 따로 할 일이 없지만 실행할 때마다 클립보드 내용이 키로 바뀜

C) 시작 실행 파일이 필요할 때만 복사 - 처음 키를 만들 때와 8000번이 아닌 포트로 시작할 때만 자동 복사. 그 밖의 경우를 위해 A의 전용 파일도 함께 제공

D) Other (please describe after [Answer]: tag below)

[Answer]: A

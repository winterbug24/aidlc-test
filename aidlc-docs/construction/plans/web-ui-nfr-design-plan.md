## 질문 범주 평가 결과

모든 범주를 평가했고, 사용자에게 물어야 할 미정 사항은 남아 있지 않다.

| 범주 | 판단 | 근거 |
|---|---|---|
| Resilience Patterns | 질문 없음 | 제한 시간(15초), 서버 응답 대기(20초), 실패 시 기존 상태 유지가 NFR 요구사항과 기능 설계에서 확정됨. 복원력 테스트 방식(RESILIENCY-14)은 1차의 사용자 답변(계획 제안)을 유지하기로 요구사항 단계에서 승인됨 |
| Scalability Patterns | 질문 없음 | 단일 사용자, 단일 프로세스 전제 유지. 화면 추가로 달라지는 것 없음 |
| Performance Patterns | 질문 없음 | 요청 수(첫 화면 4회, 동작당 1회)와 파일 구성(각 1개)이 확정됨 |
| Security Patterns | 질문 없음 | 헤더 값, 화면 파일 제공 방식, 키 처리 방식이 NFR 요구사항에서 확정됨. 포트 판정 방식은 아래 환경 확인으로 정함 |
| Logical Components | 질문 없음 | 큐, 캐시 등 인프라 컴포넌트를 추가하지 않음. 컴포넌트 구성은 기능 설계의 프런트엔드 컴포넌트와 기술 스택 결정에서 정해짐 |

## 환경 확인 결과 (2026-10-12, 이 PC에서 직접 확인)

실행 파일의 포트 판정 방식을 정하기 위해 실제 동작을 확인했다.

| 확인한 것 | 결과 | 설계 반영 |
|---|---|---|
| WSL에서 띄운 서버를 Windows에서 호출 | 된다 (200) | 서버는 WSL에서 띄우고 브라우저는 Windows에서 연다 |
| Windows 프로그램이 쓰는 포트를 WSL 안에서 확인 | 보이지 않는다 (연결 거부, 같은 포트에 바인딩도 성공) | Windows 쪽 포트 사용 여부를 따로 확인해야 한다 |
| Windows에서 닫힌 포트에 연결 시도 | 실패 판정까지 약 2초 걸린다 | 포트마다 연결을 시도하는 방식은 느리다(10개에 약 20초). Windows의 수신 포트 목록을 한 번에 읽는 방식을 쓴다 |
| WSL에서 Windows 실행 파일 호출 | `clip.exe`, `cmd.exe` 등 호출 가능 | 클립보드 복사, 브라우저 열기, 수신 포트 목록 조회에 사용 |

이 결과로 포트 판정에서 "이 서버인지" 확인하는 호출을 WSL 안에서만 하도록 정했다. 이 서버는 항상 WSL에서 실행되기 때문이다. 그래서 기능 설계에서 수용 위험으로 적었던 "다른 로컬 프로그램에 키 헤더가 전달될 수 있음"의 범위가 Windows 프로그램을 제외한 WSL 안의 프로그램으로 줄었다.

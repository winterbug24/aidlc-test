# 업무 로직 모델 - todo-api

규칙 번호(BR-xx)는 business-rules.md, 불변 조건(INV-xx)은 domain-entities.md를 가리킨다.

## 1. 공통 처리 순서

보호된 동작(`/todos` 하위)은 항상 아래 순서로 처리한다. 앞 단계에서 실패하면 뒤 단계는 수행하지 않는다.

```text
1. 요청 제한 확인        -> 초과 시 429
2. 인증 확인             -> 실패 시 401
3. 요청 형식 검증        -> 실패 시 400 / 413 / 415
4. 대상 항목 확인        -> 없으면 404 (id가 있는 동작만)
5. 업무 규칙 적용        -> 위반 시 409
6. 저장                  -> 실패 시 500, 변경 사항 없음
7. 변경 기록             -> 실제로 변경된 경우만
8. 응답
```

상태 확인은 1번(요청 제한)만 거친 뒤 바로 처리한다.

## 2. 기능별 처리 흐름

### 2.1 할 일 추가 (FR-01)
- **입력**: 본문 `title`
- **흐름**:
  1. 본문이 JSON 객체인지, 정의되지 않은 필드가 없는지, `title`이 있는지 확인 (BR-10, 11, 12)
  2. `title`이 문자열인지 확인하고 앞뒤 공백 제거 (BR-01, 02)
  3. 길이와 제어 문자 검사 (BR-03, 04)
  4. 활성 항목 중 대소문자를 무시하고 같은 제목이 있는지 확인하고, 없으면 미완료 상태로 저장. 이 판정과 저장은 원자적이다 (BR-06, 08)
  5. 생성 기록 (BR-70)
- **출력**: 201, 생성된 Todo 표현

### 2.2 목록 조회 (FR-02)
- **입력**: 쿼리 `completed` (선택)
- **흐름**:
  1. 정의되지 않은 쿼리 파라미터가 없는지, `completed` 값이 유효한지 확인 (BR-14, 15)
  2. 활성 항목을 조회하고 필터 적용 (BR-20, 22)
  3. 최신 순 정렬 (BR-21)
- **출력**: 200, `todos` 키에 Todo 표현의 배열 (없으면 빈 배열)

### 2.3 단건 조회 (FR-03)
- **입력**: 경로 id
- **흐름**: 활성 항목에서 id로 조회 (BR-16, 20, 24)
- **출력**: 200, Todo 표현

### 2.4 완료 상태 변경 (FR-04)
- **입력**: 경로 id, 본문 `completed`
- **흐름**:
  1. 본문 검증: JSON 객체, 정의되지 않은 필드 없음, `completed`가 불리언 (BR-10, 11, 12, 13)
  2. 활성 항목에서 대상 확인 (BR-33)
  3. 현재 값과 다르면 변경하고 기록, 같으면 아무것도 하지 않음 (BR-30, 31, 70)
- **출력**: 200, 현재 Todo 표현

### 2.5 삭제 (FR-05)
- **입력**: 경로 id
- **흐름**:
  1. 활성 항목에서 대상 확인 (BR-41)
  2. 삭제 시각 기록 (BR-40)
  3. 삭제 기록 (BR-70)
- **출력**: 204, 본문 없음

### 2.6 상태 확인 (FR-06)
- **입력**: 없음
- **흐름**: 저장소에 간단한 읽기를 수행해 접근 가능한지 확인
- **출력**: 200 `{"status": "ok"}`, 접근 불가 시 503 `service_unavailable` 오류 응답. 할 일 데이터나 내부 정보는 포함하지 않는다

## 3. API 계약

| 기능 | 메서드와 경로 | 인증 | 요청 | 성공 | 가능한 오류 |
|---|---|---|---|---|---|
| 추가 | `POST /todos` | 필요 | 본문 `{"title": 문자열}` | 201 Todo | 400, 401, 409, 413, 415, 429 |
| 목록 조회 | `GET /todos` | 필요 | 쿼리 `completed=true` 또는 `false` (선택) | 200 `{"todos": [Todo, ...]}` | 400, 401, 429 |
| 단건 조회 | `GET /todos/<id>` | 필요 | - | 200 Todo | 401, 404, 429 |
| 완료 상태 변경 | `PATCH /todos/<id>` | 필요 | 본문 `{"completed": 불리언}` | 200 Todo | 400, 401, 404, 413, 415, 429 |
| 삭제 | `DELETE /todos/<id>` | 필요 | - | 204 (본문 없음) | 401, 404, 429 |
| 상태 확인 | `GET /health` | 공개 | - | 200 `{"status": "ok"}` | 429, 503 |

모든 경로에서 예상하지 못한 오류는 500, 지원하지 않는 메서드는 405다.
API 키를 전달하는 헤더 이름은 NFR Design 단계에서 확정한다.

### 요청/응답 예시

할 일 추가 요청 본문:
```json
{"title": "우유 사기"}
```

응답 (201):
```json
{"id": 1, "title": "우유 사기", "completed": false, "created_at": "2026-10-12T05:00:00Z"}
```

목록 조회 응답 (200):
```json
{"todos": [{"id": 2, "title": "책 반납", "completed": true, "created_at": "2026-10-12T06:00:00Z"}, {"id": 1, "title": "우유 사기", "completed": false, "created_at": "2026-10-12T05:00:00Z"}]}
```

## 4. 오류 응답 형식

모든 오류는 아래 구조를 사용한다 (BR-60).

| 키 | 타입 | 설명 |
|---|---|---|
| `error.code` | 문자열 | business-rules.md의 오류 코드 |
| `error.message` | 문자열 | 사람이 읽을 수 있는 설명. 클라이언트가 경고창 등에 그대로 표시할 수 있다 |
| `error.details` | 배열 (선택) | 검증 오류일 때 문제 항목 목록. 각 항목은 `field`와 `reason`을 가진다 |

정의되지 않은 필드가 포함된 요청의 응답 (400):
```json
{"error": {"code": "validation_error", "message": "요청에 허용되지 않는 필드가 있습니다.", "details": [{"field": "priority", "reason": "unknown_field"}]}}
```

제목 중복 응답 (409):
```json
{"error": {"code": "duplicate_title", "message": "같은 제목의 할 일이 이미 있습니다."}}
```

### 검증 오류 reason 값

| reason | 의미 |
|---|---|
| `unknown_field` | 정의되지 않은 필드 또는 쿼리 파라미터 |
| `required` | 필수 필드 없음 |
| `invalid_type` | 타입이 맞지 않음 |
| `too_short` | 정규화 후 빈 제목 |
| `too_long` | 200자 초과 |
| `invalid_characters` | 제어 문자 또는 짝이 맞지 않는 서로게이트 문자 포함 |
| `invalid_value` | 허용되지 않는 값 (예: `completed=yes`) |
| `invalid_json` | 본문을 JSON으로 해석할 수 없음 (Code Generation 단계에서 추가) |

## 5. 오용 시나리오 (SECURITY-11)

| ID | 시나리오 | 대응 |
|---|---|---|
| MU-01 | API 키를 무작위로 대입해 추측 | 요청 제한(BR-53), 인증 실패 기록(BR-71), 상수 시간 비교(NFR-SEC-03) |
| MU-02 | 인증 없이 id를 순서대로 조회해 항목 존재 여부 파악 | 인증을 가장 먼저 검사하고 실패 시 항상 401 (BR-52) |
| MU-03 | 제목에 SQL 조각을 넣어 주입 시도 | 모든 SQL은 파라미터 바인딩 (NFR-SEC-05). 제목은 데이터로만 취급 |
| MU-04 | 제목에 스크립트 태그를 넣어 XSS 시도 | HTML을 제공하지 않고 JSON만 반환 (BR-05). 원문을 HTML에 넣을 때의 이스케이프는 클라이언트 책임임을 README에 명시 |
| MU-05 | 제목에 줄바꿈을 넣어 로그 위조 | 제어 문자 거부 (BR-04), 구조화 로깅 (NFR-SEC-06) |
| MU-06 | 매우 큰 본문 또는 대량 요청으로 자원 소진 | 본문 크기 상한 (BR-17), 요청 제한 (BR-53) |
| MU-07 | 같은 제목을 동시에 등록해 중복 금지 우회 | 판정과 저장의 원자성 (BR-08) |
| MU-08 | 오류를 유발해 내부 구조 파악 | 일반적인 오류 메시지만 반환 (BR-62) |

**수용한 위험**: 페이지네이션이 범위 밖이므로 항목이 매우 많아지면 목록 응답이 커진다. 로컬 단일 사용자용이고 요청 제한이 생성 속도를 억제하므로 수용한다.

## 6. 테스트 가능한 속성 (PBT-01)

| ID | 범주 | 속성 | 강제 여부 |
|---|---|---|---|
| P-01 | Round-trip | 유효한 제목 t로 생성한 뒤 조회하면 제목은 t의 앞뒤 공백을 제거한 값과 같다 | 강제 (PBT-02) |
| P-02 | Round-trip | Todo를 저장소 행으로 바꿨다가 다시 표현으로 바꾸면 id, title, completed, created_at이 같다 | 강제 (PBT-02) |
| P-03 | Invariant | `completed` 필터 조회 결과의 모든 항목은 요청한 완료 상태다 | 강제 (PBT-03) |
| P-04 | Invariant | 삭제한 항목은 이후 목록에도 단건 조회에도 나타나지 않는다 | 강제 (PBT-03) |
| P-05 | Invariant | 목록은 항상 최신 순으로 정렬되어 있다 | 강제 (PBT-03) |
| P-06 | Invariant | 활성 항목의 제목은 대소문자를 무시하면 모두 다르다 (INV-01) | 강제 (PBT-03) |
| P-07 | Invariant | 유효하지 않은 제목(빈 문자열, 201자 이상, 제어 문자 포함)은 항상 400이고 항목 수는 변하지 않는다 | 강제 (PBT-03) |
| P-08 | Idempotence | 같은 `completed` 값을 두 번 설정한 결과는 한 번 설정한 결과와 같다 | 권고 (PBT-04) |
| P-09 | Stateful | 임의의 추가/변경/삭제 순서를 단순한 메모리 모델과 실제 API에 함께 적용하면 목록 결과가 항상 일치한다 | 권고 (PBT-06) |

제너레이터 요구 (PBT-07): 유효 제목(1~200자, 한글 등 유니코드 포함, 제어 문자 제외, 앞뒤 공백이 붙은 변형 포함)과 유효하지 않은 제목을 각각 재사용 가능한 제너레이터로 정의한다.

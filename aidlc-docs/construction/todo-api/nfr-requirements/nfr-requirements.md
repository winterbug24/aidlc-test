# NFR 요구사항 - todo-api

요구사항 문서(`aidlc-docs/inception/requirements/requirements.md`) 4장의 NFR을 측정 가능한 수준으로 구체화한다.
근거 표기: NFR-Q는 NFR Requirements 질문 번호를 가리킨다.

## 1. 전제와 가정

| 항목 | 내용 |
|---|---|
| 실행 환경 | 로컬 PC 전용 (WSL Ubuntu 기준으로 검증, Waitress를 사용하므로 Windows에서도 실행 가능) |
| 사용 규모 | 동시 사용자 1명, 활성 항목 수천 건 이하 (가정) |
| 프로세스 구성 | 단일 프로세스, 다중 스레드 (Waitress) |
| 워크로드 중요도 | Low (NFR-RES-01) |

## 2. 성능 및 확장성

| ID | 요구사항 | 기준 |
|---|---|---|
| PERF-01 | 로컬 단일 사용자 사용에서 체감 지연이 없어야 한다 | 활성 항목 1,000건 기준 목록 조회 응답 200ms 이내 (설계 목표, 별도 부하 테스트 대상은 아님) |
| PERF-02 | 목록 조회와 중복 판정이 항목 수 증가에 따라 급격히 느려지지 않아야 한다 | 중복 판정과 활성 항목 조회에 인덱스 사용 |
| SCAL-01 | 수평 확장은 요구하지 않는다 | 단일 프로세스 전제. 요청 제한 카운터가 메모리에 있으므로 다중 프로세스 구성은 지원 범위 밖 |

## 3. 가용성 및 복구

| ID | 요구사항 | 기준 | 근거 |
|---|---|---|---|
| AVAIL-01 | 가용성 목표(SLA)는 정의하지 않는다 | 로컬 개인용 | NFR-RES-02 |
| AVAIL-02 | RTO/RPO는 수 시간, DR 전략은 백업 및 복원 | 백업 스크립트 실행 주기는 사용자 재량 | NFR-RES-02 |
| AVAIL-03 | 백업/복원 스크립트를 제공한다 | SQLite 온라인 백업 기능으로 타임스탬프가 붙은 사본 생성, 생성 직후 무결성 검사, 최근 7개 보관, 수동 실행 | NFR-Q8:A |
| AVAIL-04 | 복원 절차와 복원 후 검증 방법을 README에 문서화한다 | 서버 중지, 파일 교체, 상태 확인 호출 순서 | RESILIENCY-13 |
| AVAIL-05 | 백업 파일은 DB 파일과 같은 수준으로 보호한다 | 소유자 전용 권한, 암호화된 볼륨 전제 | RESILIENCY-12, SECURITY-01 |

## 4. 신뢰성

| ID | 요구사항 | 기준 | 근거 |
|---|---|---|---|
| REL-01 | SQLite 연결에 명시적 타임아웃을 둔다 | busy timeout 5초 | NFR-RES-05 |
| REL-02 | DB 연결은 요청 단위로 열고 성공/실패와 무관하게 닫는다 | 오류 시 트랜잭션 롤백 | NFR-SEC-09 |
| REL-03 | 상태 확인은 DB 읽기 가능 여부를 확인한다 | 실패 시 503 | FR-06 |
| REL-04 | 필수 설정(API 키)이 없으면 시작을 거부한다 | 명확한 오류 메시지 출력 후 종료 | NFR-SEC-02 |
| REL-05 | DB 파일과 스키마가 없으면 시작 시 자동으로 만든다 | 반복 실행해도 안전 (멱등) | 운영 편의 |

## 5. 보안

요구사항 문서의 NFR-SEC-01~15를 그대로 적용하며, 이 단계에서 확정한 수치는 다음과 같다.

| ID | 요구사항 | 기준 | 근거 |
|---|---|---|---|
| SEC-01 | 요청 제한 | 클라이언트 IP당 분당 60회. 인증 실패는 IP당 분당 10회 | NFR-Q5:A |
| SEC-02 | 요청 제한 구현 | Flask-Limiter, 메모리 저장소 (재시작 시 카운터 초기화) | NFR-Q4:A |
| SEC-03 | 요청 본문 크기 상한 | 16KB (제목 200자 기준으로 충분) | NFR-SEC-04 |
| SEC-04 | 입력 검증 | 자체 스키마 검증 모듈. 모든 핸들러가 이 모듈을 거친다 | NFR-Q3:A |
| SEC-05 | API 키 최소 길이 | 32자 이상. 미달이면 시작 거부. README에 안전한 키 생성 방법 안내 | NFR-SEC-02 |
| SEC-06 | 서버 바인딩 | 기본 127.0.0.1. 환경 변수로 변경 가능하되 README에 위험 안내 | NFR-SEC-13 |
| SEC-07 | 의존성 취약점 스캔 | pip-audit을 CI와 로컬 절차 모두에서 실행 | NFR-SEC-12 |
| SEC-08 | 의존성 고정 | 직접 및 하위 의존성 모두 `==`로 고정 | NFR-Q2:A |
| SEC-09 | CI 구성 요소 고정 | GitHub Actions의 액션과 Python 버전을 고정된 버전으로 지정 (`latest` 금지) | SECURITY-10 |
| SEC-10 | 로그 파일 보호 | 소유자 전용 권한으로 생성 | NFR-SEC-06 |

## 6. 관측 가능성

| ID | 요구사항 | 기준 | 근거 |
|---|---|---|---|
| OBS-01 | JSON 구조화 로그 | 필드: 타임스탬프(UTC), 레벨, 요청 ID, 메시지, 이벤트별 부가 정보 | NFR-SEC-06 |
| OBS-02 | 로그 출력 위치 | 표준 출력 + 로컬 로그 파일 | NFR-Q7:B |
| OBS-03 | 로그 파일 순환 | 크기 기준 5MB, 최근 5개 보관 | NFR-Q7:B |
| OBS-04 | 요청 로그 | 요청마다 메서드, 경로, 상태 코드, 처리 시간 기록. 제목 본문과 API 키는 기록하지 않음 | NFR-SEC-06 |
| OBS-05 | 요청 ID | 요청마다 생성해 로그와 응답 헤더에 포함 | NFR-SEC-06 |
| OBS-06 | 변경 기록 | 생성/상태 변경/삭제 시 대상 id와 변경 전후 값 | NFR-SEC-07 |
| OBS-07 | 보안 이벤트 기록 | 인증 실패, 요청 제한 초과 | BR-71 |

로그 보관 기간: 크기 기준 순환을 선택했으므로 기간 단위 보관(예: 90일)은 보장하지 않는다. 로컬 개인용이며 준수해야 할 규정이 없어 SECURITY-14의 보관 기간 항목은 N/A로 판단한다.

## 7. 변경 및 배포 관리

| ID | 요구사항 | 기준 | 근거 |
|---|---|---|---|
| CHG-01 | 변경 관리 프로세스 면제 | 로컬 개인용 도구. 변경 이력은 git | 추가 질문 6:C |
| CHG-02 | CI 도구는 GitHub Actions | 저장소에 기존 워크플로가 없으므로 호환되는 워크플로 파일을 새로 작성한다. 푸시와 풀 리퀘스트에서 테스트(속성 기반 테스트 포함)와 pip-audit 실행 | NFR-Q9:A |
| CHG-03 | 자동 배포는 없다 | 로컬 전용이라 CI는 검증까지만 수행 | 추가 질문 4:A |
| CHG-04 | 롤백은 버전 고정 방식 | git에서 이전 커밋/태그로 되돌린 뒤 의존성 재설치, 재시작 | NFR-Q10:A |
| CHG-05 | 배포 방식은 직접/제자리 교체 | 프로세스 중지 후 새 코드로 재시작. 중요도 Low와 부합 | NFR-Q11:A |
| CHG-06 | 스키마 변경 시 롤백 | 현재 범위에는 마이그레이션이 없다. 스키마를 바꾸는 변경 전에는 백업을 먼저 수행하도록 README에 안내 | RESILIENCY-04 |

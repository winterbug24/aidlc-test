# NFR 설계 패턴 - todo-api

NFR 요구사항(`../nfr-requirements/nfr-requirements.md`)의 각 항목을 어떤 패턴으로 충족하는지 정의한다.
근거 표기: ND-Q는 NFR Design 질문 번호를 가리킨다.

## 1. 보안 패턴

### SP-01 기본 거부 인증 (Deny by Default)
- 보호 대상 라우트 묶음(`/todos` 전체)에 요청 전처리 훅으로 인증을 건다. 라우트를 추가해도 자동으로 보호된다.
- 공개 라우트(`/health`)는 별도 묶음으로 분리하고 코드에 공개임을 명시한다.
- API 키는 `X-API-Key` 헤더로 받는다 (ND-Q2:A).
- 비교는 표준 라이브러리의 상수 시간 비교를 사용한다. 헤더가 없거나 형식이 달라도 같은 401 응답을 준다.
- 충족: SEC NFR-SEC-01, 03, 11 / SECURITY-08, 11

### SP-02 시작 시 설정 검증 (Fail Closed)
- 설정은 환경 변수에서 한 번 읽어 검증한다. API 키가 없거나 32자 미만이면 예외를 던져 시작을 중단한다.
- 기본 키, 예시 키를 코드에 두지 않는다.
- 충족: REL-04, SEC-05 / SECURITY-09, 12, 15

### SP-03 선언적 입력 검증
- 엔드포인트별 스키마(허용 필드, 필수 여부, 타입, 길이, 문자 제약)를 한 곳에 선언하고, 공통 검증 함수가 스키마로 본문과 쿼리를 검사한다.
- 검증 함수는 모든 문제를 모아 `details` 목록으로 반환한다 (BR-61).
- 핸들러는 검증을 통과한 정규화된 값만 사용한다.
- 본문 크기 상한 16KB는 프레임워크 설정으로 적용한다.
- 충족: SEC-03, 04 / SECURITY-05

### SP-04 파라미터 바인딩 전용 데이터 접근
- SQL은 저장소 컴포넌트 안에만 두고, 모든 값은 자리표시자로 바인딩한다. SQL 문자열에 입력 값을 끼워 넣지 않는다.
- 충족: NFR-SEC-05 / SECURITY-05

### SP-05 2단 요청 제한
- 1단: 모든 라우트에 클라이언트 IP당 분당 60회.
- 2단: 보호 라우트에 "인증 실패 응답(401)만 차감하는" 분당 10회 한도를 추가한다. 정상 호출은 이 한도를 소모하지 않는다.
- 클라이언트 식별은 직접 연결된 원격 주소만 사용한다. 프록시 전달 헤더는 신뢰하지 않는다.
- 초과 시 429와 `Retry-After` 헤더를 반환한다.
- 카운터는 프로세스 메모리에 둔다 (단일 프로세스 전제, SCAL-01).
- 충족: SEC-01, 02 / SECURITY-11

### SP-06 전역 오류 변환
- 모든 HTTP 오류(404, 405, 413, 415, 429 등)와 업무 오류를 공통 JSON 오류 형식으로 변환하는 처리기를 앱 수준에 등록한다.
- 처리되지 않은 예외는 최상위 처리기가 잡아 요청 ID와 함께 상세를 로그에 남기고, 응답에는 일반 메시지의 500만 보낸다.
- 디버그 모드는 기본 비활성이며 설정으로 켤 수 없게 한다.
- 충족: NFR-SEC-08 / SECURITY-09, 15

### SP-07 최소 노출
- 서버는 기본적으로 127.0.0.1에 바인딩한다.
- CORS 헤더를 보내지 않는다.
- 응답은 JSON만 반환하고 `X-Content-Type-Options: nosniff`, `Cache-Control: no-store` 헤더를 붙인다 (심층 방어).
- DB 파일, 백업 파일, 로그 파일과 그 디렉터리는 소유자 전용 권한으로 만든다.
- 충족: SEC-06, SEC-10, NFR-SEC-14, 15 / SECURITY-01, 07, 08

### SP-08 공급망 관리
- 의존성은 두 개의 고정 파일로 관리하고 CI와 로컬 절차에서 pip-audit을 실행한다.
- CI 워크플로의 액션과 Python 버전은 고정된 버전으로 지정한다.
- 충족: SEC-07, 08, 09 / SECURITY-10

## 2. 복원력 패턴

### RP-01 요청 단위 연결과 확실한 정리
- DB 연결은 요청 처리 중 처음 필요할 때 열고, 요청 종료 훅에서 성공/실패와 무관하게 닫는다.
- 쓰기는 트랜잭션으로 묶어 성공 시 커밋, 예외 시 롤백한다.
- 충족: REL-02 / SECURITY-15, RESILIENCY-10

### RP-02 명시적 타임아웃과 1회 재시도
- 연결에 busy timeout 5초를 설정한다.
- 잠금으로 실패하면 같은 작업을 한 번만 다시 시도한다. 다시 실패하면 503 `service_unavailable`과 `Retry-After` 헤더를 반환한다 (ND-Q4:B).
- 재시도 대상은 잠금/바쁨 오류뿐이다. 제약 위반이나 그 밖의 오류는 재시도하지 않는다.
- 최악의 경우 응답 시간은 약 10초다.
- 충족: REL-01 / RESILIENCY-10

### RP-03 WAL 저널
- DB 초기화 시 WAL 모드를 켠다 (ND-Q3:A). 읽기와 쓰기가 서로 막지 않아 다중 스레드 서버에서 잠금 경합이 줄고 비정상 종료 후에도 일관성이 유지된다.
- 보조 파일(`-wal`, `-shm`)이 생기므로 백업과 복원은 반드시 제공 스크립트로 한다.
- 충족: REL-01, AVAIL-03 / RESILIENCY-10, 12

### RP-04 제약 기반 중복 방지
- "활성 항목의 제목은 대소문자를 무시하면 유일하다"(INV-01)를 DB의 부분 유일 인덱스로 강제한다. 인덱스 대상은 삭제되지 않은 행이고 비교는 영문 대소문자 무시다.
- 생성은 바로 삽입을 시도하고 제약 위반을 409로 변환한다. 사전 조회 후 삽입하는 방식보다 동시 요청에 안전하다 (BR-08, MU-07).
- 이 인덱스는 중복 판정 성능도 담당한다 (PERF-02).

### RP-05 깊은 상태 확인
- `/health`는 DB에 간단한 읽기를 수행한다. 실패하면 503을 반환한다.
- 충족: REL-03 / RESILIENCY-06

### RP-06 멱등 초기화
- 시작 시 DB 디렉터리, 파일, 스키마, 인덱스를 "없으면 생성"으로 만든다. 여러 번 실행해도 결과가 같다.
- 충족: REL-05

### RP-07 온라인 백업과 검증된 복원
- 백업: SQLite 온라인 백업 기능으로 실행 중에도 일관된 사본을 만든다. 파일 이름에 UTC 타임스탬프를 넣고, 생성 직후 사본에 무결성 검사를 수행한다. 검사에 실패한 사본은 삭제하고 오류로 종료한다. 성공하면 최근 7개만 남긴다.
- 복원: 대상 백업의 무결성을 먼저 검사한다. 현재 DB는 안전 사본으로 따로 남긴 뒤 교체하고 보조 파일을 정리한다. 복원 전 서버 중지와 복원 후 상태 확인 호출을 절차에 포함한다.
- 충족: AVAIL-03, 04, 05 / RESILIENCY-11, 12, 13

## 3. 관측 가능성 패턴

### OP-01 요청 ID 전파
- 요청 시작 시 요청 ID를 생성해 요청 컨텍스트에 두고, 그 요청에서 나오는 모든 로그와 응답 헤더(`X-Request-ID`)에 포함한다.
- 클라이언트가 보낸 요청 ID 헤더는 사용하지 않는다 (로그 위조 방지).

### OP-02 JSON 구조화 로그
- 표준 로깅에 JSON 포매터를 붙여 한 줄에 한 이벤트를 기록한다. 필드: `timestamp`(UTC), `level`, `request_id`, `event`, `message`와 이벤트별 부가 필드.
- 출력은 표준 출력과 순환 로그 파일(5MB, 5개) 두 곳이다.

### OP-03 이벤트 분류

| event | 시점 | 부가 필드 |
|---|---|---|
| `request` | 모든 요청 종료 시 | 메서드, 경로, 상태 코드, 처리 시간(ms), 원격 주소 |
| `todo_created` | 생성 반영 후 | id |
| `todo_completion_changed` | 상태가 실제로 바뀐 후 | id, 변경 전 값, 변경 후 값 |
| `todo_deleted` | 삭제 반영 후 | id |
| `auth_failed` | 인증 실패 | 원격 주소, 경로 |
| `rate_limited` | 요청 제한 초과 | 원격 주소, 경로 |
| `db_retry` | 잠금으로 재시도 | 작업 이름 |
| `unhandled_error` | 처리되지 않은 예외 | 예외 종류, 스택 트레이스 (로그에만) |

- 제목 본문과 API 키는 어떤 이벤트에도 기록하지 않는다.
- 충족: OBS-01~07 / SECURITY-03, 13, RESILIENCY-05

## 6. 복원력 테스트 계획 (RESILIENCY-14, ND-Q1:B)

기존 관행이 없으므로 아래 계획을 제안한다.

### 6.1 자동화 테스트 (CI와 로컬에서 매번 실행)

| ID | 시나리오 | 기대 결과 |
|---|---|---|
| RT-01 | 다른 연결이 DB를 잠근 상태에서 쓰기 요청 | 1회 재시도 후 503과 `Retry-After`, `db_retry` 로그 |
| RT-02 | 잠금이 재시도 중에 풀림 | 요청 성공 |
| RT-03 | DB에 접근할 수 없는 상태에서 `/health` 호출 | 503 |
| RT-04 | DB 접근 오류 중 보호 라우트 호출 | 내부 정보 없는 일반 오류 응답, 부분 반영 없음 |
| RT-05 | 백업 후 데이터 변경, 그 백업으로 복원 | 복원 후 데이터가 백업 시점과 일치 |
| RT-06 | 손상된 백업 파일로 복원 시도 | 복원 거부, 현재 DB는 그대로 |
| RT-07 | 백업을 8회 이상 수행 | 최근 7개만 남음 |
| RT-08 | API 키 없이 또는 짧은 키로 시작 | 시작 거부 |

테스트에서는 타임아웃을 짧게 설정해 실행 시간을 줄인다.

### 6.2 수동 복원 훈련

| 항목 | 내용 |
|---|---|
| 주기 | 분기 1회, 그리고 스키마를 바꾸는 변경을 적용하기 전 |
| 절차 | 백업 실행, 서버 중지, 복원 스크립트 실행, 서버 시작, `/health` 확인, 목록 조회로 데이터 확인 |
| 측정 | 복원에 걸린 시간을 기록해 RTO(수 시간) 이내인지 확인 |
| 결과 기록 | 저장소의 훈련 기록 문서에 날짜, 소요 시간, 문제점, 조치 사항을 남긴다 |

Operations 단계는 자리표시자이므로, 훈련 실행은 사용자가 README 절차에 따라 수행한다.

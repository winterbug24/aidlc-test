# 논리 컴포넌트 - todo-api

패턴 번호(SP, RP, OP, PP, TP)는 `nfr-design-patterns.md`를 가리킨다.
파일 이름과 디렉터리 배치는 Code Generation 계획에서 확정한다.

## 1. 컴포넌트 목록

| ID | 컴포넌트 | 책임 | 적용 패턴 |
|---|---|---|---|
| C-01 | 설정 (Config) | 환경 변수 읽기, 기본값 적용, 필수 값 검증, 시작 거부 | SP-02 |
| C-02 | 앱 팩토리 (App Factory) | 설정을 받아 앱을 조립: 로깅, DB, 요청 제한, 오류 처리기, 라우트 등록 | TP-01, SP-06 |
| C-03 | 인증 (Auth) | `X-API-Key` 검증, 실패 시 401과 `auth_failed` 이벤트 | SP-01 |
| C-04 | 요청 제한 (Rate Limiting) | 전체 한도와 인증 실패 한도 적용, 429 응답 | SP-05, TP-02 |
| C-05 | 검증 (Validation) | 엔드포인트별 스키마 선언, 본문/쿼리 검증, 제목 정규화 | SP-03, TP-03 |
| C-06 | 저장소 (Todo Repository) | Todo의 생성, 조회, 상태 변경, 논리 삭제 SQL. 제약 위반을 업무 오류로 변환 | SP-04, RP-04, PP-01 |
| C-07 | DB 연결 관리 (Database) | 요청 단위 연결, 타임아웃, WAL, 스키마 초기화, 잠금 시 1회 재시도, 파일 권한 | RP-01, RP-02, RP-03, RP-06, SP-07 |
| C-08 | 할 일 라우트 (Todo Routes) | 5개 보호 엔드포인트. 검증, 저장소 호출, 응답 직렬화, 변경 이벤트 기록 | SP-01, OP-03 |
| C-09 | 상태 확인 라우트 (Health Route) | 공개 엔드포인트. DB 읽기 확인 | RP-05 |
| C-10 | 오류 처리 (Errors) | 업무 오류 정의, 공통 JSON 오류 형식, 전역 처리기 | SP-06 |
| C-11 | 로깅 (Logging) | JSON 포매터, 출력 대상 구성, 요청 ID, 요청 로그 | OP-01, OP-02, OP-03 |
| C-12 | 직렬화 (Serialization) | 저장소 행과 Todo 표현(JSON) 사이의 변환 | TP-03 |
| C-13 | 서버 진입점 (Server Entry) | 설정을 읽어 Waitress로 앱 실행 | SP-07 |
| C-14 | 백업/복원 스크립트 (Backup Tools) | 온라인 백업, 무결성 검사, 보관 개수 관리, 검증된 복원 | RP-07 |
| C-15 | CI 워크플로 (CI Workflow) | GitHub Actions에서 테스트와 취약점 스캔 실행 | SP-08 |

큐, 캐시, 서킷 브레이커, 외부 서비스 클라이언트는 두지 않는다 (PP-02).

## 2. 의존 관계

```text
C-13 Server Entry
  -> C-01 Config
  -> C-02 App Factory
       -> C-11 Logging
       -> C-07 Database
       -> C-04 Rate Limiting
       -> C-10 Errors
       -> C-08 Todo Routes
       |    -> C-03 Auth
       |    -> C-05 Validation
       |    -> C-06 Todo Repository -> C-07 Database
       |    -> C-12 Serialization
       -> C-09 Health Route -> C-07 Database

C-14 Backup Tools -> C-01 Config (DB 경로만 사용, 앱과 독립 실행)
C-15 CI Workflow  -> 테스트와 의존성 고정 파일
```

의존 규칙:
- 라우트만 프레임워크의 요청/응답 객체를 다룬다. 검증(C-05), 직렬화(C-12)는 프레임워크에 의존하지 않는 순수 함수다.
- SQL은 저장소(C-06)와 DB 연결 관리(C-07)에만 있다.
- 인증(C-03)은 다른 업무 컴포넌트에 의존하지 않는다.

## 3. 요청 처리 파이프라인

```text
요청 수신
  1. 요청 ID 생성, 시작 시각 기록        (C-11)
  2. 본문 크기 상한 확인                 (프레임워크 설정)   -> 413
  3. 요청 제한 확인                      (C-04)              -> 429
  4. 인증 확인 (보호 라우트만)           (C-03)              -> 401
  5. 본문/쿼리 검증과 정규화             (C-05)              -> 400, 415
  6. 저장소 호출                         (C-06, C-07)        -> 404, 409, 503
  7. 변경 이벤트 기록                    (C-11)
  8. 응답 직렬화                         (C-12)
  9. 공통 응답 헤더 추가, 요청 로그 기록 (C-11)
 10. DB 연결 닫기                        (C-07)
어느 단계의 오류든 전역 처리기(C-10)가 공통 JSON 오류 형식으로 변환한다.
```

기능 설계의 공통 처리 순서(요청 제한, 인증, 형식 검증, 대상 확인, 업무 규칙, 저장)와 일치한다.

## 4. 데이터 저장 설계

### 테이블 `todos`

| 컬럼 | 타입 | 제약 |
|---|---|---|
| `id` | 정수 | 기본 키, 자동 증가(재사용 없음) |
| `title` | 텍스트 | NOT NULL, 길이 1~200 검사 제약 |
| `completed` | 정수 (0/1) | NOT NULL, 기본값 0, 0 또는 1 검사 제약 |
| `created_at` | 텍스트 (ISO 8601 UTC) | NOT NULL |
| `deleted_at` | 텍스트 (ISO 8601 UTC) | NULL 허용 |

### 인덱스

| 인덱스 | 대상 | 목적 |
|---|---|---|
| 활성 제목 유일 인덱스 | `title` (영문 대소문자 무시), `deleted_at`이 NULL인 행만 | INV-01 강제, 중복 판정 (RP-04) |
| 활성 항목 목록 인덱스 | `created_at`, `id` 내림차순, `deleted_at`이 NULL인 행만 | 최신 순 목록 조회 (PP-01) |

검증 계층(C-05)과 DB 제약이 같은 규칙을 이중으로 지킨다 (심층 방어).

## 5. 설정 항목 (확정)

| 환경 변수 | 필수 | 기본값 | 설명 |
|---|---|---|---|
| `TODO_API_KEY` | 예 | 없음 | API 키, 32자 이상 |
| `TODO_DB_PATH` | 아니오 | `instance/todo.db` | SQLite 파일 경로 |
| `TODO_LOG_DIR` | 아니오 | `logs` | 로그 파일 디렉터리 |
| `TODO_BACKUP_DIR` | 아니오 | `backups` | 백업 파일 디렉터리 |
| `TODO_HOST` | 아니오 | `127.0.0.1` | 바인딩 주소 |
| `TODO_PORT` | 아니오 | `8000` | 포트 |

상대 경로는 프로젝트 루트 기준이다. `instance/`, `logs/`, `backups/`는 버전 관리에서 제외한다.
요청 제한 한도, DB 타임아웃 등은 환경 변수로 노출하지 않고 앱 팩토리의 설정 인자로만 바꿀 수 있다 (테스트 전용, TP-02).

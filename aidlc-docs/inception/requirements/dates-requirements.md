# 요구사항 문서: 등록 일자와 완료 일자 표시 (4차 워크플로)

1차(`requirements.md`), 2차(`web-ui-requirements.md`), 3차(`stop-server-requirements.md`)의 요구사항은 그대로 유효하다. 이 문서는 추가되거나 바뀌는 요구사항만 다룬다.

## 1. 의도 분석 요약

| 항목 | 내용 |
|---|---|
| 사용자 요청 | "현재 http://127.0.0.1:8000/api_test 이 url 로 들어가면, 해당 페이지가 열리는데 작업 리스트에 네모 체크박스 옆에 작업 등록 일자 (yyyy/mm/dd), 완료 일자(yyyy/mm/dd) 포함시켜줘" |
| 요청 유형 | Enhancement (기존 할 일 목록 화면과 데이터 모델 확장) |
| 범위 | Multiple Components (DB 스키마, 저장소, 직렬화, API 응답, 웹 화면) |
| 복잡도 | Moderate. 화면 표시 자체는 단순하지만 완료 시각을 새로 저장해야 하므로 기존 DB 파일의 구조 변경이 따른다 |
| 요구사항 깊이 | Standard |
| 프로젝트 유형 | Brownfield. 리버스 엔지니어링 산출물은 3차 워크플로의 변경까지 반영되어 최신이므로 다시 수행하지 않음 |

### 현재 상태 (코드 확인 결과)
- 등록 시각은 `todos.created_at`에 UTC ISO 8601 문자열(`2026-10-14T07:25:02.123456Z`)로 저장되고 API 응답에도 있다. 화면에는 표시하지 않는다.
- 완료 여부는 `todos.completed`(0 또는 1)만 저장한다. **완료 시각은 저장하지 않는다.**
- 스키마는 서버 시작 시 `CREATE TABLE IF NOT EXISTS`로 만들며, 기존 테이블에 열을 추가하는 이전(migration) 장치는 없다.

## 2. 확인 질문 답변 요약

질문 파일: `dates-requirement-verification-questions.md`

| 질문 | 답변 | 결정 |
|---|---|---|
| Q1 기존 완료 항목의 완료 일자 | A | 비워 두고 "완료 -"로 표시. 날짜를 지어내지 않음 |
| Q2 완료 해제 시 | A | 완료 일자를 지움. 다시 체크하면 그 시각으로 새로 기록 |
| Q3 표시 시간대 | A | 브라우저(Windows)의 시간대 기준. 저장은 UTC 유지 |
| Q4 미완료 항목의 완료 일자 자리 | A | 등록 일자만 보이고 완료 일자 자리는 비움 |
| Q5 배치 | A | 체크 상자와 제목 사이에 한 줄로: `[ ] 등록 2026/10/14 · 완료 2026/10/16  장보기  [삭제]` |
| Q6 API에 `completed_at` 추가 | A | 추가. 미완료면 `null`. 기존 필드 유지 |
| Q7 확장 설정 | A | 유지 (Security 적용, Resiliency 적용, PBT 부분 적용) |

### 답변을 조합하며 정한 세부 사항 (승인 단계에서 바꿀 수 있음)
- **"완료 -"와 빈칸의 구분**: 완료 상태인데 완료 시각이 없으면(Q1) "완료 -"로 표시하고, 미완료면(Q4) 완료 일자 글자를 표시하지 않는다.
- **줄 맞춤**: Q5-A처럼 날짜가 제목 앞에 오면, 미완료 행에서 완료 일자를 빼는 순간 제목의 시작 위치가 행마다 달라진다. 그래서 미완료 행에서도 완료 일자 자리의 폭은 비워 둔 채 남겨, 모든 행의 제목이 같은 위치에서 시작하게 한다. 글자는 보이지 않으므로 Q4-A("자리는 비운다")와 맞다.
- **좁은 화면**: 창 폭이 좁아 한 줄에 다 들어가지 않으면 날짜 묶음이 제목 위로 줄바꿈되는 것을 허용한다. 제목이 잘리거나 가로 스크롤이 생기지 않게 한다.

## 3. 기능 요구사항

### DFR-01 완료 시각 저장
- 할 일을 완료로 바꾸면 그 시각(UTC)을 `completed_at`에 저장한다.
- 완료를 해제하면 `completed_at`을 비운다(NULL).
- 이미 완료인 할 일에 다시 완료를 요청하면(값 변화 없음) `completed_at`을 바꾸지 않는다. 미완료 할 일에 미완료를 요청해도 마찬가지다. 기존의 "변화 없는 요청" 동작과 같다.
- 새로 추가한 할 일은 미완료이므로 `completed_at`이 비어 있다.

### DFR-02 기존 DB 이전
- 서버가 시작될 때 기존 `todos` 테이블에 `completed_at` 열이 없으면 추가한다. 이미 있으면 아무것도 하지 않는다(여러 번 실행해도 안전).
- 기존 행의 `completed_at`은 비워 둔다(Q1-A). 완료 상태인 기존 행도 마찬가지다.
- 기존 데이터(제목, 완료 여부, 등록 시각, 삭제 기록)는 바뀌지 않는다.

### DFR-03 API 응답
- 할 일 표현(추가, 목록, 단건 조회, 완료 상태 변경의 응답)에 `completed_at`을 추가한다. 값은 `created_at`과 같은 UTC ISO 8601 형식 문자열이거나 `null`이다.
- 기존 필드(`id`, `title`, `completed`, `created_at`)의 이름, 형식, 의미는 바꾸지 않는다. 요청 형식도 바꾸지 않는다. 클라이언트가 `completed_at`을 보낼 수 있는 경로는 만들지 않는다(서버만 기록).

### DFR-04 화면 표시
- 할 일 목록의 각 행에서 체크 상자와 제목 사이에 날짜를 두 줄로 표시한다: 첫 줄 `등록 yyyy/mm/dd`, 둘째 줄 `완료 yyyy/mm/dd`. (2026-10-14 변경 요청으로 한 줄에서 두 줄로 바꾸고 구분점 `·`을 없앰. 같은 요청으로 페이지 최대 폭을 42rem에서 48rem으로 넓혀 입력 칸과 제목 영역을 늘림)
- 날짜는 브라우저 시간대 기준이며, 형식은 `yyyy/mm/dd`(월과 일은 두 자리)다.
- 완료 상태이고 완료 시각이 있으면 `완료 yyyy/mm/dd`, 완료 상태인데 완료 시각이 없으면 `완료 -`, 미완료면 완료 일자 글자를 표시하지 않는다(자리 폭은 유지).
- 체크 상자를 눌러 완료/해제하면 서버 응답의 `completed_at`으로 그 행의 완료 일자가 바로 바뀐다.
- 날짜 값이 형식에 맞지 않으면 화면이 깨지지 않고 해당 날짜를 `-`로 표시한다.

### DFR-05 접근성과 조작
- 날짜 글자는 화면 읽기 프로그램이 "등록 2026년 10월 14일"처럼 의미를 알 수 있게 읽을 수 있어야 한다(`<time datetime>` 등 사용).
- 체크 상자와 제목을 눌러 완료를 바꾸는 기존 동작, 키보드 조작(Tab, Space, Enter, Esc), 삭제 버튼의 이름(`삭제: 제목`)은 바꾸지 않는다. 날짜 영역을 눌렀을 때의 동작은 기존 행 클릭 동작을 따른다.

### 범위에 포함하지 않는 것
- 날짜로 정렬하거나 거르는 기능
- 날짜 형식이나 시간대를 화면에서 바꾸는 설정
- 시각(시:분) 표시
- 기존 완료 항목의 완료 일자를 사용자가 직접 입력하는 기능

## 4. 비기능 요구사항

| ID | 요구사항 | 관련 규칙 |
|---|---|---|
| DNFR-01 | DB 이전은 열 추가만 한다(기존 열 변경, 삭제, 데이터 재작성 없음). 이전 버전 코드는 새 열을 무시하므로, 문제가 생기면 코드만 이전 커밋으로 되돌려도 동작한다 | RESILIENCY-04 (DB를 고려한 되돌리기) |
| DNFR-02 | 이전은 한 트랜잭션에서 수행하고, 실패하면 서버가 시작을 거부하고 로그에 남긴다. 반쯤 바뀐 상태로 서버가 뜨지 않는다 | SECURITY-15, RESILIENCY-04 |
| DNFR-03 | README에 "업데이트 전에 `python -m todo_api.backup backup`으로 백업"하는 안내를 둔다. 기존 백업 도구와 복원 절차는 그대로 쓸 수 있어야 한다(백업 사본에 새 열이 있어도, 없어도 복원 가능) | RESILIENCY-12 |
| DNFR-04 | `completed_at`은 서버 시각으로만 기록한다. 요청 본문의 알 수 없는 필드를 거부하는 기존 검증은 유지한다 | SECURITY-05 |
| DNFR-05 | 화면은 날짜를 `textContent` 등 텍스트로만 넣는다. 서버 값으로 HTML을 만들지 않는다. 외부 날짜 라이브러리를 추가하지 않는다(브라우저 기본 기능 사용). 콘텐츠 보안 정책(CSP)은 바꾸지 않는다 | SECURITY-04, SECURITY-05, SECURITY-10 |
| DNFR-06 | 날짜 표시는 기존 밝게/어둡게 테마와 대비 기준(WCAG 2.1 AA)을 따른다. 보조 정보이므로 제목보다 작고 흐리게 하되 대비 4.5:1 이상 | 2차 웹 화면 NFR |
| DNFR-07 | 직렬화의 왕복(저장소 행 ↔ Todo)과 날짜 형식 변환에 속성 기반 테스트를 추가한다. 도메인 생성기는 기존 `tests/strategies.py`를 확장한다 | PBT-02, PBT-03, PBT-07 |
| DNFR-08 | 기존 자동 테스트 324개는 모두 통과해야 한다. 바뀐 응답 형식에 맞춰 고쳐야 하는 테스트는 기대값에 `completed_at`을 더하는 변경만 허용한다 | 회귀 방지 |
| DNFR-09 | 목록 조회 성능은 기존과 같은 수준을 유지한다(새 인덱스 불필요, 쿼리 형태 유지) | - |

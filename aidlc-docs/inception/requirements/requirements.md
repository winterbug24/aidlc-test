# 요구사항 문서: Flask To-Do 관리 REST API

## 1. 의도 분석 요약

| 항목 | 내용 |
|---|---|
| 사용자 요청 | 파이썬 Flask로 간단한 할 일(To-Do) 관리 REST API 작성. 할 일 추가/조회/완료처리/삭제 기능, 저장은 SQLite. 모든 문서와 질문은 한국어 |
| 요청 유형 | New Project (신규 프로젝트, Greenfield) |
| 범위 | Single Component (단일 Flask 애플리케이션) |
| 복잡도 | Simple (단순 CRUD). 단, 보안/복원력 확장 적용으로 비기능 요구사항이 추가됨 |
| 요구사항 깊이 | Standard |
| 실행 환경 | 로컬 PC에서만 실행 (학습/개인용, 배포 없음) |

## 3. 기능 요구사항

### FR-01 할 일 추가
- 제목(title)을 받아 새 할 일을 생성한다.
- 새 항목은 미완료 상태로 생성되며, id와 생성 시각은 서버가 부여한다.
- 제목은 필수이며 문자열이어야 한다. 앞뒤 공백 제거 후 1자 이상 200자 이하.
- 성공 시 생성된 항목을 반환한다 (HTTP 201).

### FR-02 할 일 목록 조회
- 삭제되지 않은 모든 할 일을 반환한다 (HTTP 200).
- `completed` 쿼리 파라미터(`true`/`false`)로 완료 여부를 필터링할 수 있다.
- `completed` 값이 `true`/`false`가 아니면 HTTP 400을 반환한다.
- 페이지네이션은 범위에 포함하지 않는다.

### FR-03 할 일 단건 조회
- id로 할 일 하나를 조회한다 (HTTP 200).
- 존재하지 않거나 논리 삭제된 id는 HTTP 404를 반환한다.

### FR-04 완료 상태 변경
- id로 지정한 할 일의 완료 여부를 `true` 또는 `false`로 변경한다 (완료 취소 가능).
- 같은 상태로 다시 변경해도 오류 없이 현재 상태를 반환한다 (멱등).
- 존재하지 않거나 논리 삭제된 id는 HTTP 404를 반환한다.

### FR-05 할 일 삭제 (논리 삭제)
- id로 지정한 할 일에 삭제 표시(삭제 시각 기록)를 한다. DB의 행은 제거하지 않는다.
- 삭제된 항목은 FR-02, FR-03, FR-04에서 존재하지 않는 것으로 취급한다.
- 이미 삭제된 항목이나 존재하지 않는 id의 삭제 요청은 HTTP 404를 반환한다.
- 삭제된 항목의 조회/복구 기능은 제공하지 않는다.

### FR-06 상태 확인(Health Check)
- 프로세스 동작과 DB 연결 가능 여부를 확인하는 엔드포인트를 제공한다 (RESILIENCY-06).
- 이 엔드포인트는 의도적으로 공개(인증 불필요)이며 할 일 데이터를 노출하지 않는다.

### 범위에 포함하지 않는 것
- 제목 수정, 상세 설명/마감일/우선순위, 페이지네이션, 사용자 계정, 삭제 항목 복구, 웹 UI

### 데이터 모델 (요구사항 수준)

| 필드 | 타입 | 설명 |
|---|---|---|
| id | 정수 | 자동 증가 기본 키 |
| title | 문자열 (1~200자) | 할 일 제목 |
| completed | 불리언 | 완료 여부, 기본값 false |
| created_at | 시각 (UTC, ISO 8601) | 생성 시각 |
| deleted_at | 시각 또는 NULL | 논리 삭제 시각. API 응답에는 포함하지 않음 |

### API 초안 (세부 사항은 설계 단계에서 확정)

| 기능 | 메서드와 경로 | 성공 응답 |
|---|---|---|
| 추가 | `POST /todos` | 201 |
| 목록 조회 | `GET /todos` (선택: `?completed=true` 또는 `false`) | 200 |
| 단건 조회 | `GET /todos/<id>` | 200 |
| 완료 상태 변경 | `PATCH /todos/<id>` (본문: `completed` 불리언) | 200 |
| 삭제 | `DELETE /todos/<id>` | 204 |
| 상태 확인 | `GET /health` (공개) | 200 |

요청과 응답 본문은 JSON이며, 오류 응답도 일관된 JSON 형식을 사용한다.

## 4. 비기능 요구사항

### 4.1 보안 (Security Baseline 확장 - 강제 적용)

| ID | 요구사항 | 관련 규칙 |
|---|---|---|
| NFR-SEC-01 | 모든 `/todos` 엔드포인트는 API 키 헤더 인증을 요구한다. 기본 거부(deny by default)이며 `/health`만 명시적 공개로 표시한다 | SECURITY-08 |
| NFR-SEC-02 | API 키는 환경 변수로 주입한다. 소스 코드/설정 파일에 하드코딩하지 않으며 기본 키를 두지 않는다. 키가 설정되지 않으면 애플리케이션은 시작을 거부한다(fail closed) | SECURITY-09, 12, 15 |
| NFR-SEC-03 | API 키 비교는 타이밍 공격에 안전한 상수 시간 비교를 사용한다 | SECURITY-08 |
| NFR-SEC-04 | 모든 입력(본문, 경로 id, 쿼리 파라미터)의 타입/길이/형식을 검증한다. 요청 본문 크기 상한을 설정한다 | SECURITY-05 |
| NFR-SEC-05 | 모든 SQL은 파라미터 바인딩을 사용한다. 문자열 결합으로 SQL을 만들지 않는다 | SECURITY-05 |
| NFR-SEC-06 | 구조화 로깅을 구성한다. 로그에는 타임스탬프, 요청 ID, 로그 레벨, 메시지를 포함하고 API 키는 기록하지 않는다 | SECURITY-03 |
| NFR-SEC-07 | 할 일의 생성/상태 변경/삭제는 시각과 대상 id, 변경 전후 값을 로그로 남긴다 | SECURITY-13 |
| NFR-SEC-08 | 전역 오류 처리기를 두고, 오류 응답에는 스택 트레이스나 내부 경로, DB 세부 정보를 노출하지 않는다. 디버그 모드는 기본 비활성 | SECURITY-09, 15 |
| NFR-SEC-09 | DB 오류 경로에서 연결을 닫고 트랜잭션을 롤백한다 | SECURITY-15 |
| NFR-SEC-10 | 엔드포인트에 요청 제한(rate limiting)을 적용한다. 인증 실패 반복도 제한 대상이다 | SECURITY-11 |
| NFR-SEC-11 | 인증 로직은 전용 모듈로 분리한다 | SECURITY-11 |
| NFR-SEC-12 | 의존성은 정확한 버전으로 고정하고, 취약점 스캔(예: pip-audit) 절차를 빌드 지침에 포함한다. 사용하지 않는 의존성은 두지 않는다 | SECURITY-10 |
| NFR-SEC-13 | 서버는 기본적으로 루프백 주소(127.0.0.1)에만 바인딩한다 | SECURITY-07, 09 |
| NFR-SEC-14 | SQLite DB 파일은 소유자만 읽고 쓸 수 있는 권한으로 생성하며, OS 수준 디스크 암호화가 적용된 볼륨에 두는 것을 전제로 문서화한다 | SECURITY-01 |
| NFR-SEC-15 | CORS는 활성화하지 않는다 (와일드카드 오리진 금지) | SECURITY-08 |

**SECURITY-01 관련 미결 사항**: 표준 `sqlite3` 모듈은 DB 파일 자체 암호화를 지원하지 않는다. NFR-SEC-14는 OS 디스크 암호화에 의존하는 해석이며, DB 파일 자체 암호화가 필요하면 SQLCipher 계열 라이브러리로 DB 접근 방식을 바꿔야 한다. 이 해석의 수용 여부는 검토 시 확인이 필요하다.

## 6. 핵심 요약
- 로컬에서 실행하는 단일 Flask 애플리케이션으로, 할 일 추가/목록 조회/단건 조회/완료 상태 변경/논리 삭제 5개 기능과 상태 확인 엔드포인트를 제공한다.

- API 키 인증, 입력 검증, 요청 제한, 구조화 로깅, 안전한 오류 처리를 포함한다.
- pytest 예제 기반 테스트와 Hypothesis 속성 기반 테스트를 함께 작성한다.

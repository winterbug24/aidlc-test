## 스토리 분해 방식 선택지

| 방식 | 설명 | 이 프로젝트에서의 장단점 |
|---|---|---|
| 사용자 여정 기반 | 사용 흐름 순서로 구성 (처음 시작, 키 입력, 일상 사용, 문제 상황) | 화면이 하나이고 흐름이 분명해 잘 맞는다. 자동화 테스트 시나리오로 바로 옮기기 쉽다 |
| 기능 기반 | 요구사항(WFR) 단위로 구성 | 요구사항과 1:1로 추적하기 쉽지만 첫 실행 같은 여러 기능에 걸친 흐름이 흩어진다 |
| 페르소나 기반 | 사용자 유형별로 구성 | 사용자 유형이 적어 구분할 내용이 거의 없다 |
| 도메인 기반 | 업무 영역별로 구성 | 영역이 하나(할 일)뿐이라 의미가 없다 |
| 에픽 기반 | 큰 에픽 아래 하위 스토리 | 규모에 비해 계층이 과하다 |

## Question 1
이 화면을 쓰는 사람은 누구인가요? (안내 문구의 수준과 첫 실행 흐름의 친절함이 달라집니다.)

A) 나 혼자 - 이 프로젝트를 직접 만든 개발자. WSL, 환경 변수, API 키 개념을 알고 있음

B) 나와, 같은 PC를 쓰는 기술 지식이 적은 사람(가족 등) - 터미널을 쓰지 않고 실행 파일과 화면만 사용

C) Other (please describe after [Answer]: tag below)

[Answer]: A

## Question 2
스토리를 어떤 방식으로 나눌까요? (위 "스토리 분해 방식 선택지" 참고)

A) 사용자 여정 기반 - 처음 시작하기, 키 입력하기, 할 일 관리하기, 문제 상황 대처하기 순서 (추천: 화면이 하나이고 흐름이 분명함)

B) 기능 기반 - 요구사항(WFR-01~11) 단위로 하나씩

C) Other (please describe after [Answer]: tag below)

[Answer]: A

## Question 3
수용 기준은 어떤 형식으로 쓸까요?

A) Given/When/Then 형식 (조건, 동작, 기대 결과. 자동화 테스트로 옮기기 쉬움)

B) 체크리스트 형식 (확인할 항목을 나열. 짧고 읽기 쉬움)

C) Other (please describe after [Answer]: tag below)

[Answer]: A

## Question 4
처음 실행할 때 실행 파일이 API 키를 만들어 줍니다. 그 키를 화면에 한 번 입력해야 하는데, 사용자가 키를 어떻게 알게 할까요?

A) 실행 창에 키를 표시 - 사용자가 보고 복사해 화면에 붙여넣음 (단순함. 창을 보는 사람에게 키가 보임)

B) 클립보드에 자동 복사 - 실행 파일이 키를 클립보드에 넣고 "화면에 붙여넣으세요"라고 안내. 창에는 키를 표시하지 않음 (가장 편함. 클립보드 기록에 키가 남을 수 있음)

C) 키 파일 위치만 안내 - 실행 창에 키가 저장된 파일 경로만 알려 주고 사용자가 직접 열어 복사 (키가 화면에 자동으로 드러나지 않음. 번거로움)

D) Other (please describe after [Answer]: tag below)

[Answer]: B
